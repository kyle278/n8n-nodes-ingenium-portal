# n8n Cloud starters

These use only built-in nodes and can be imported into n8n Cloud before our custom node is verified. They are setup workflows, not activated Carlow campaigns.

1. Import `01-check-connection.json`. Select a **Header Auth** credential in its HTTP node: Name `Authorization`, Value `Bearer <organisation integration key>`.
2. Run the connection check. Copy object API names and field UUIDs from its schema output into your organisation configuration.
3. Import `02-preview-audience.json`. Set the allowed object and typed `queryJson`. Select the same credential. It fetches bounded pages and flags truncation; an offset scan is not a consistent snapshot. It outputs IDs and counts rather than patient field values.
4. Import `03-test-workflow-state.json` to test `state.read` and `state.write`. The fixed probe key and operation key let an identical rerun replay the write. For a different probe use a new pair. It creates one integration-owned test item without changing client records.
5. Import `04-test-single-sms.json` only after configuring the portal SMS policy and provider. SMS stays disabled until an approved test record/message is supplied and `sendApprovedTest` is true. The portal rechecks explicit SMS permission. Keep the same operation key for the same intended send, including after a timeout. Inspect uncertain outcomes in portal operation history; never invent a new key to retry an uncertain send.

Every HTTP node needs its credential selected after import. The exports include no credentials. Automatic retries and redirects are disabled. Workflow execution payload storage is disabled in the exports; temporary manual editor output can still contain data, so use permitted test records.

The audience preview caps pages at 10 by default (up to 100). Each page holds up to 100 records, with a 600ms interval. This respects the default integration rate for the scan alone; overlapping workflows share the organisation/integration rate limits. A 429 stops the run for inspection.

Before Carlow campaign activation, confirm January day/time, active-client/status mappings, permission data, PRSI grant-use date, appointment blocking/category rules, month-end policy, backlog handling, message text, booking destination and spacing. Persistent recall enrolment and follow-up processing require their own campaign workflows; these starters do not implement them. npm publication and node verification run separately.

Generated by `node scripts/build-cloud-starters.cjs`; tested with Node and inspected against official HTTP Request configuration. Cloud import/runtime validation is recorded separately in the launch notes.
